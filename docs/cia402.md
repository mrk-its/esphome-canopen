# CANopenNode step 2b: `cia402` drive profile on the device API

## Context
Step 2 ([device_api_canopennode.md](device_api_canopennode.md)) gives profile components an SDO client, NMT master,
node monitoring, raw frames and the `CANopenNode` base class. This step ports `cia402` from esphome/esphome#21533
(on top of #21522; device subclass `tmcm1240` in #21534) onto it. As in step 2, **we keep the functionality, not the
API**.

What #21533 does (`cia402.cpp`, 345 lines; `cia402.h`, 140; `__init__.py`, 160):
- `CiA402Drive : PollingComponent, CANopenNode`; YAML `node_id`, `profile_velocity`, `acceleration`, `deceleration`,
  `quick_stop_deceleration`, `min_position`/`max_position`, `operation_timeout` (30 s), `heartbeat_timeout`
  (1500 ms), `update_interval` (500 ms), `on_result` (`DriveResult`); one drive per node (final validation).
- Actions `cia402.enable`, `disable` (controlword 0), `halt` (0x10F), `controlled_stop` (= halt), `quick_stop` (2),
  `fault_reset`, `apply_configuration`, `move_to: position`, `move_by: distance` (profile position mode, signed
  software limits checked locally and written to 0x607D).
- Everything is SDO: commands are a list of up to 32 steps (write / read / check / wait-for-bits / relative), run one
  at a time, a wait step re-reads 0x6041 every 50 ms. Between commands it polls 0x6041/0x6061/0x6064/0x606C
  round-robin every `update_interval`. Every move writes the whole profile (0x6081..0x6085, 0x607D) again.
- Heartbeat timeout and "operational" are tracked in the profile; a stop drains the request in flight
  (`pending_stop_`/`pending_sequence_` bookkeeping); EMCY with an error code fails a running command.
- Extension points used by `tmcm1240`: `virtual append_profile()` (extra 0x2011/0x2013 writes), its own
  `apply_configuration()` (currents, StallGuard registers), `write_()`/`read_()` step builders.

## Goals
- **Process data by PDO.** Statusword, position, velocity and mode display come from the drive's TPDOs;
  controlword and target position go to its RPDO with `send_pdo()`. No SDO polling, no 50 ms re-reads: state
  transitions and "target reached" are seen on the frame that reports them.
- **SDO only for configuration** (PDO mapping, mode of operation, profile, limits, device registers), run once when
  the drive comes online and again after it resets (`on_node_reset()`), and on `apply_configuration`.
- **Node state from the hub** (`on_node_online/offline/reset`, `is_operational()`); no `heartbeat_seen_` /
  `last_heartbeat_ms_` in the profile.
- **Stops never wait behind SDO**: a stop is one RPDO frame. Only if the drive isn't OPERATIONAL (PDOs not
  processed) it falls back to `cancel_sdo(this)` + `write_sdo(0x6040)`.
- Same YAML and actions as #21533 where they still make sense, so its esphome.io docs (esphome/esphome.io#7889)
  mostly carry over.

Out of scope (as in #21533): homing, position zeroing, velocity/torque modes, unit scaling (raw drive units),
drives whose PDOs can't be remapped (SDO-only mode, see "Open points"), `tmcm1240` itself (but the extension points
must fit it).

## Changes

### 1. `canopen`: `SDOSequence`, `configure_rpdo()` / `configure_tpdo()`
- `SDOSequence` (in `canopen_node.h`, only with `USE_CANOPEN_SDO_CLIENT`): a fixed list of SDO writes
  (`std::array<Write, N>`, `Write {index, sub, value, size}`, default N = 48) run one after another on
  `write_sdo()`, with one completion callback `(SDOResult, abort_code, failed index/sub)`. Stops at the first error.
  `add(index, sub, value, size)` / `add<T>(index, sub, T)` build it; `start(cb)`, `cancel()` (→ `cancel_sdo(this)`,
  no callback), `running()`. Owned by the profile (one per node), so `cancel_sdo()`'s context is the sequence.
  Overflow at `add()` → `start()` calls back `REJECTED` (one result path, as in step 2).
- `CANopenNode::configure_tpdo(SDOSequence &, n, cob_id, transmission_type, inhibit_100us, event_timer_ms,
  std::initializer_list<PdoEntry>)` and `configure_rpdo(SDOSequence &, n, cob_id, transmission_type, entries)`,
  `PdoEntry {index, sub, bits}`. They append the CiA 301 order: COB-ID with bit 31 set (disable) → mapping sub0 = 0
  → mapping entries (`index << 16 | sub << 8 | bits`) → mapping sub0 = count → transmission type, inhibit time,
  event timer (TPDO only) → COB-ID without bit 31 (enable). `n` is 1-based (0x1400/0x1600/0x1800/0x1A00 + n - 1);
  `cob_id = 0` means the predefined set (TPDO n: `0x80 + n * 0x100 + node`, RPDO n: `0x100 + n * 0x100 + node`, for
  n = 1..4).
- Some drives reject PDO mapping writes in OPERATIONAL (abort `0x08000022`): the helper doesn't change NMT state,
  the profile puts the node in PRE_OPERATIONAL first (see below).
- Tests: a host unit test of the sequence and the generated write list (like `test/logs`, stub `write_sdo`), and on
  hardware the step 2 test node 0x01 (old esphome-canopen node; canopen-stack accepts 0x1800/0x1A00 writes).

### 2. `components_next/cia402`
Files: `__init__.py`, `cia402.h`, `cia402.cpp`. `class CiA402Drive : public Component, public canopen::CANopenNode`
(no `PollingComponent`: nothing is polled). Codegen: `await canopen.register_node(var, config, sdo=True, nmt=True,
heartbeat_timeout=config[CONF_HEARTBEAT_TIMEOUT])`.

**PDO layout** (written by the configuration sequence; `n` and COB-IDs are the predefined set):

| Drive PDO | Content | Size | Transmission |
|---|---|---|---|
| TPDO1 (`0x180 + node`) | statusword 0x6041, position actual 0x6064 | 6 bytes | 255 (event), event timer = `update_interval` |
| TPDO2 (`0x280 + node`) | velocity actual 0x606C, mode display 0x6061 | 5 bytes | 255, event timer = `update_interval` |
| RPDO1 (`0x200 + node`) | controlword 0x6040, target position 0x607A | 6 bytes | 255 |

- Statusword and position in one frame: "target reached" and the final position arrive together. Controlword and
  target in one frame: a new set-point is one frame (target + bit 4), no ordering issue between two writes.
- Event timer as the refresh rate: changes of state (statusword) are sent at once by most drives with type 255;
  position/velocity are refreshed every `update_interval` (default 100 ms; also how the profile detects stale data,
  next to the hub's heartbeat monitoring). Inhibit time 0.
- Listeners: `add_pdo_listener(0x180 + node)` / `(0x280 + node)` → `on_tpdo1_()` / `on_tpdo2_()` decode
  (little-endian, length checked; a short frame → warning, ignored).
- RPDO1 frames carry the current `controlword_` and `target_` members; `send_control_(controlword)` updates
  `controlword_` and sends one frame.

**Configuration** (`configure_()`, an `SDOSequence`; on `on_node_online()`, `on_node_reset()` and
`apply_configuration`):
1. `send_nmt(PRE_OPERATIONAL)` (PDO mapping), then the sequence:
2. `configure_tpdo(1..2)`, `configure_rpdo(1)` as above;
3. mode of operation 0x6060 = 1 (profile position);
4. profile: 0x6081 profile velocity, 0x6083 acceleration, 0x6084 deceleration, 0x6085 quick stop deceleration
   (default = deceleration), 0x607D:1/2 limits if set;
5. `virtual void append_configuration(SDOSequence &)` (default: nothing): device registers (`tmcm1240`: currents,
   StallGuard, its 0x2011/0x2013 profile copies);
6. on success `send_nmt(START)`; `configured_ = true` once the drive reports OPERATIONAL (`on_node_nmt_changed`).
- While not configured, commands are rejected (`REJECTED`). A failed sequence logs the failing index/abort code,
  sets a warning and retries on the next `on_node_reset()` / `apply_configuration` (no automatic retry loop).
- The profile is written only here, not before every move (#21533 writes 4-6 objects per move).
- Option `start_node: true` (default): set `false` when another master manages NMT on this bus; then the profile
  only configures and waits for OPERATIONAL.

**State machine** (driven by TPDO1, no SDO):
- `DriveState state_from_statusword()` and the `DriveState` / `DriveResult` enums as in #21533 (names shortened:
  `DriveState::OPERATION_ENABLED`, `DriveResult::SUCCESS`, ...).
- One command at a time (`Command {kind, target, deadline}`), each a small table of `(controlword, wait for state /
  bits)` transitions: on every TPDO1 the current step is checked and the next controlword sent.
  - `enable`: (if FAULT → `FAULT`) 0x06 → READY_TO_SWITCH_ON → 0x07 → SWITCHED_ON → 0x0F → OPERATION_ENABLED;
    steps whose state is already reached are skipped.
  - `fault_reset`: 0x00 → 0x80 (rising edge of bit 7) → statusword bit 3 clear → 0x00 (mask as in #21533).
  - `move_to(p)` / `move_by(d)`: requires OPERATION_ENABLED and mode display 1; limit check (`move_by`: on
    `position_ + d`, from TPDO1, 64-bit); `target_ = p`, send 0x0F with bit 4 (0x1F, absolute, "change set
    immediately" 0) → wait statusword bit 12 (set-point acknowledge) → 0x0F → wait bit 10 (target reached), then
    `SUCCESS`.
  - `halt` (0x10F), `quick_stop` (0x02), `disable` (0x00): cancel the running command (`CANCELLED`), send at once,
    `SUCCESS` when the statusword confirms (halt: bit 10 with bit 8 set; quick stop: QUICK_STOP_ACTIVE or
    SWITCH_ON_DISABLED; disable: SWITCH_ON_DISABLED). If the node isn't OPERATIONAL: `cancel_sdo(this)` +
    `write_sdo<uint16_t>(0x6040)`, result from the SDO reply.
- Failures: statusword bit 3 (fault) during a command → `FAULT` (except in `fault_reset`); `operation_timeout`
  (checked in `loop()`, only while a command runs; `disable_loop()` otherwise) → `TIMEOUT`; `on_node_offline()` or
  NMT leaving OPERATIONAL → `COMMUNICATION_ERROR`; `on_node_reset()` → `COMMUNICATION_ERROR` + reconfigure.
- EMCY (`on_node_emcy`): logged with error code/register; a non-zero error code fails a running command (`FAULT`),
  as in #21533. `get_last_emergency()` for lambdas.
- Results: every command ends in exactly one `on_result` call (also rejections, synchronously).

**Public API** (lambdas, subclasses): `enable()`, `disable()`, `halt()`, `quick_stop()`, `fault_reset()`,
`move_to()`, `move_by()`, `apply_configuration()`, `get_state()`, `get_statusword()`, `get_position()`,
`get_velocity()`, `get_mode()`, `is_target_reached()`, `is_configured()`, `busy()`,
`add_on_result_callback()`, `add_on_update_callback()` (after every TPDO; replaces #21533's `value_callback_`).
Subclass hooks: `append_configuration(SDOSequence &)`, `on_update()`.

**YAML** (`cia402:`, `MULTI_CONF`):
- kept from #21533: `canopen_id`, `node_id`, `profile_velocity`, `acceleration`, `deceleration`,
  `quick_stop_deceleration`, `min_position`/`max_position` (together, min ≤ max), `operation_timeout` (30 s),
  `heartbeat_timeout` (now the hub's `monitor_node()` timeout, default 1500 ms), `on_result` (`result`);
- changed: `update_interval` is the TPDO event timer (1 ms..65535 ms, default 100 ms), not an SDO poll period;
- new: `start_node` (default `true`);
- dropped: `controlled_stop` action (alias of `halt`);
- actions: `cia402.enable`, `disable`, `halt`, `quick_stop`, `fault_reset`, `apply_configuration`, `move_to:
  position` (templatable), `move_by: distance` (templatable);
- final validation: one `cia402` per `(canopen_id, node_id)` (from #21533), `node_id` != the hub's own node id.

   - online → configuration sequence (PRE_OPERATIONAL, mapping writes, START), TPDO1/TPDO2 every `update_interval`;
   - `enable` → controlwords 6/7/15 one TPDO after another, `SUCCESS`; no SDO frames after configuration;
   - `move_to: 1000` → one RPDO with target + bit 4, set-point ack, target reached, `SUCCESS`, `get_position()`
     1000; `move_by: -500`; `move_to` outside the limits → `REJECTED` without frames;
   - `quick_stop` during a move: the RPDO leaves within one loop (timestamp vs. the button press), `CANCELLED` for
     the move, then `SUCCESS`; same for `halt`;
   - drive in fault → `FAULT`; `fault_reset` → `SUCCESS`;
   - drive reset (NMT reset from the host) → `COMMUNICATION_ERROR` for a running command, reconfiguration, enable
     works again; drive unplugged → `COMMUNICATION_ERROR`, configuration on the next ONLINE.
4. `tmcm1240` fit: sketch the #21534 subclass in the scratchpad on `append_configuration()` and compile it against
   `components_next` (as step 2 did for `cia402`).

## Open points
- **Test device.** Is a CiA 402 drive available (the TMCM-1240 of #21533, or another)? Otherwise a simulator: a
  Python script with `canopen` (`LocalNode` with a minimal CiA 402 OD: 0x6040/0x6041 state machine, profile
  position with a simple ramp, PDO comm/mapping objects) on the host CAN interface used by can2mqtt. It would live
  in `test/` so later steps can use it.
- **Drives that don't support PDO remapping / dynamic mapping.** Options: map only what the drive's default
  mapping offers (`pdo_mapping: default`, read 0x1A00/0x1600 instead of writing them), or an SDO-only mode like
  #21533. Neither is in this step; decide when such a drive shows up.
- **NMT ownership.** With `start_node: true` the profile sends PRE_OPERATIONAL/START to its node. Several profiles
  on one node, or another NMT master on the bus (e.g. a PLC), need `start_node: false`. Should can2mqtt ever send NMT
  to drives?
- **RPDO timeout on the drive** (0x1400 sub5 event timer / 0x6007 abort connection option): makes the drive stop
  when our node dies. Needs a cyclic RPDO from us (every `update_interval`). Probably worth it for safety; adds
  steady bus load. Not in this step unless the test drive needs it.
- **SYNC-based (transmission type 1) PDOs** for multi-axis coordination: needs a SYNC producer in our node
  (CANopenNode `CO_SYNC`, `CO_CONFIG_SYNC`); later.
